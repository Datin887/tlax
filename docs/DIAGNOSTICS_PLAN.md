# 🔍 TLAX — Полный план диагностики проекта

**Версия:** 1.0 (2026-09-02)
**Проект:** tlax.ru — студия персонализированных песен
**Стек:** PHP 8.5 (nginx + PHP-FPM), MySQL 8, Vanilla JS, FastPanel (5.35.100.174)
**Цель документа:** единый алгоритм проверок — что, как, когда и зачем проверять, чтобы проект не «умирал молча».

---

## 🧭 Логика плана

Проверки делятся на **4 уровня регулярности** + **триггерные**:

| Уровень | Когда | Формат | Кто |
|---|---|---|---|
| **L0** | Каждый день | Автомат (cron) | Миша |
| **L1** | Раз в неделю | Полуавтомат + e2e | Миша |
| **L2** | Раз в месяц | Аудит | Миша + Boss |
| **L3** | После изменений | Чек-лист регресса | Миша |
| **T** | По событию | Точечная проверка | Миша |

Главный принцип: **сначала критичное для денег и данных, потом красота**.

Приоритеты бизнеса TLAX (по убыванию):
1. 💰 **Заказы не теряются** (анкета → БД → уведомление Boss)
2. 🔐 **Данные клиентов целы** (БД, бэкапы)
3. 🎵 **Контент продаёт** (треки играют, тарифы видны, портфолио живое)
4. ⚡ **Сайт быстрый и доступный**
5. 🧹 **Гигиена сервера** (логи, мусор, права)

## L0 — ЕЖЕДНЕВНО (автомат, ~2 мин)

Зачем: поймать «молчаливую смерть» в первые часы, а не через неделю (как было с .env 31.07 → 02.09).

### 0.1 Доступность сайта
- **Что:** GET всех публичных страниц, код ответа 200
- **Как:** curl по списку URL (главная, pricing, order, portfolio, contacts, privacy, thank-you, admin/login)
- **Когда:** ежедневно утром (и после любых правок)
- **Зачем:** клиент не должен видеть 500. Если страница упала — сразу чинить
- **Порог:** любая страница ≠ 200 → алерт

### 0.2 Рост errors.log
- **Что:** размер и хвост `logs/errors.log`
- **Как:** SFTP, смотрим размер (был 12.8 МБ когда БД лежала!) + последние 20 строк
- **Когда:** ежедневно
- **Зачем:** лог растёт = что-то сыпется. Размер > 5 МБ за сутки = проблема
- **Действие:** читаем ошибку → чиним причину → чистим/ротируем лог

### 0.3 БД жива
- **Что:** SELECT 1 / количество заказов/треков
- **Как:** через API get-tracks ({"success":true}) + прямой запрос через временный скрипт
- **Когда:** ежедневно
- **Зачем:** БД умирала (root:root 600 на .env) → без неё мёртвы админка, заказы, портфолио
- **Контроль:** env.config.php читается, DB_PASS не пустой

### 0.4 SSL-сертификат
- **Что:** дата истечения
- **Как:** openssl s_client / curl -v
- **Когда:** ежедневно
- **Зачем:** протухший SSL = браузер пугает клиента = потеря заказов
- **Порог:** < 14 дней до истечения → алерт

### 0.5 Новая заявка?
- **Что:** количество заказов в БД за сутки
- **Как:** SELECT COUNT(*) FROM orders WHERE created_at > NOW() - INTERVAL 1 DAY
- **Когда:** ежедневно
- **Зачем:** если заказы есть, а Boss не знает — сломаны уведомления; если заказов нет вообще — может, сломана анкета
- **Порог:** заказы есть и уведомление не ушло → чинить почту

## L1 — ЕЖЕНЕДЕЛЬНО (~15–20 мин)

Зачем: проверить, что клиентский путь реально работает end-to-end, а не «страница открывается».

### 1.1 E2E: заказ-сценарий (главный!)
- **Что:** пройти анкету целиком: главная → order → 6 шагов → submit → заявка в БД → письмо на datinvasy@gmail.com
- **Как:** браузер (headless) + проверка БД (новая строка в orders) + проверка почты
- **Когда:** еженедельно, и после любой правки order.php/submit-order.php
- **Зачем:** это ДЕНЬГИ. Если submit сломан или CSRF блочит — заказы молча теряются
- **Проверки:** валидация, rate limit, honeypot не мешают, фото загружается, песня уходит

### 1.2 Уведомления Boss
- **Что:** письмо реально уходит на почту (SMTP/mail())
- **Как:** тестовый заказ → проверить входящие datinvasy@gmail.com (или лог mail.log)
- **Когда:** еженедельно
- **Зачем:** мы поменяли ADMIN_EMAIL на datinvasy@gmail.com — надо убедиться, что письма реально доходят, а не падают в спам
- **Проблема:** SMTP_HOST/SMTP_PASS пустые — mail() может не работать на хостинге → нужен SMTP или Telegram

### 1.3 Контент: треки и обложки
- **Что:** все 10 треков из БД → файлы существуют, не 0 байт, аудио проигрывается
- **Как:** сравнить audio_url/cover_url в БД с файлами на SFTP (assets/uploads/tracks/, covers/)
- **Когда:** еженедельно
- **Зачем:** битая ссылка на трек = клиент не слышит пример = нет заказа
- **Порог:** любой 404/0 байт → перезалить или убрать трек

### 1.4 Админка
- **Что:** вход, список заказов, CRUD треков, статистика
- **Как:** headless-браузер под admin/admin123
- **Когда:** еженедельно
- **Зачем:** Boss должен управлять сайтом; если админка падает — блокировка бизнеса
- **Внимание:** сменить admin123 на нормальный пароль (планируется)

### 1.5 Форма контактов
- **Что:** отправка → строка в contact_messages + письмо
- **Как:** тестовая отправка через contacts.php
- **Когда:** еженедельно
- **Зачем:** лиды с «остались вопросы» не должны теряться

### 1.6 Синхронизация Git ↔ сервер
- **Что:** локальный репозиторий vs сервер (расхождение после правок контактов/конфига)
- **Как:** diff ключевых файлов; закоммитить актуальное состояние
- **Когда:** еженедельно
- **Зачем:** сервер ушёл вперёд от GitHub — надо вернуть синхрон, иначе потеряем правки

## L2 — ЕЖЕМЕСЯЧНО (аудит, ~1 час)

Зачем: глубокая проверка здоровья и безопасности — профилактика до того, как случится.

### 2.1 Безопасность (полная)
- **Что:**
  - `.env` / `env.config.php` не отдаются через web
  - CSRF на всех формах (order, contact, admin login)
  - Rate limiting работает (5 попыток/15 мин логин, 5 заказов/час)
  - Honeypot не обходится
  - SQL-инъекции (prepared statements везде)
  - Загрузка файлов: только картинки/аудио, размеры, расширения
  - Права файлов: конфиги не 777, uploads не исполняемые
  - Папки: public/, public_html/, api.bak/, cleanup-*.php — мусор на сервере, удалить или понять зачем
- **Как:** ручной аудит кода + сканеры (nuclei/ nikto опционально) + проверка прав
- **Когда:** ежемесячно + после крупных изменений
- **Зачем:** сайт хранит персональные данные клиентов (имена, телефоны, фото, истории) — утечка = репутация + 152-ФЗ

### 2.2 Пароли и доступы
- **Что:** пересмотреть все пароли (админка, SFTP, MySQL), сменить слабые
- **Как:** список доступов в MEMORY.md, смена admin123
- **Когда:** ежемесячно
- **Зачем:** admin123 — открытая дверь; SFTP/MySQL пароли засвечены в чате/файлах

### 2.3 Производительность
- **Что:** TTFB каждой страницы, размер HTML/CSS/JS, вес картинок, кэш, gzip, число запросов к БД на страницу
- **Как:** curl -w, PageSpeed/Lighthouse (опционально), EXPLAIN тяжёлых запросов
- **Когда:** ежемесячно
- **Зачем:** скорость = конверсия; 3 сек против 1 сек = -30–50% заказов на мобильных
- **Порог:** TTFB > 800 мс, страница > 2 МБ → оптимизировать

### 2.4 Инфраструктура
- **Что:**
  - Свободное место на диске
  - Бэкапы БД и файлов (есть ли вообще? сделать план!)
  - PHP error_reporting в production (сейчас APP_ENV=development — display_errors ВКЛЮЧЕН — это дыра!)
  - PHP-версия, обновления
  - Крон-задачи (если есть)
  - Логи: ротация (errors.log, rate_cache, mail.log)
- **Как:** SFTP/FastPanel + скрипт
- **Когда:** ежемесячно
- **Зачем:** диск забился / бэкапов нет = потеря всего. APP_ENV=development светит ошибки клиентам

### 2.5 Здоровье БД
- **Что:** CHECK TABLE, размер, дубли, неиспользуемые таблицы (v_orders_summary?), индексы на orders.created_at
- **Как:** SQL-запросы через временный скрипт
- **Когда:** ежемесячно
- **Зачем:** растущая БД без индексов = тормоза; дубли = мусор в отчётах

### 2.6 SEO / внешний вид
- **Что:** sitemap.xml актуален, robots.txt, meta на страницах, 404-страница, favicon, OG-теги
- **Как:** curl + визуальный осмотр
- **Когда:** ежемесячно
- **Зачем:** поисковики приводят трафик; битые ссылки/дубли = падение в выдаче

## L3 — ПОСЛЕ ИЗМЕНЕНИЙ (чек-лист регресса, ~10 мин)

Зачем: каждое изменение (фикс, фича, деплой) не должно ломать соседнее (урок: «проверка соседних блоков»).

### 3.1 Чек-лист после любого изменения
- [ ] Все публичные страницы 200
- [ ] API get-tracks успешен
- [ ] Вход в админку работает
- [ ] Создать/отредактировать тестовый трек → сохранился
- [ ] Анкета: шаги листаются, submit проходит (тестовая заявка)
- [ ] Нет новых ошибок в errors.log
- [ ] env-файлы не отдаются через web
- [ ] Git-коммит сделан (если менялся код)

### 3.2 Чек-лист после правки БД/конфига
- [ ] DB-коннект из PHP (не только из CLI)
- [ ] Права на .env/env.config.php корректны
- [ ] Все страницы, ходящие в БД (index, portfolio, admin), живы
- [ ] Бэкап перед изменением сделан

## T — ТРИГГЕРНЫЕ (по событию)

| Событие | Проверка |
|---|---|
| Boss жалуется «не работает» | Полный L0 + конкретная страница + логи |
| После деплоя | L3 чек-лист |
| После смены хостинга/DNS | DNS, SSL, редиректы, www/без www, HTTP→HTTPS |
| После правки .env/конфига | L3.2 |
| Подозрение на взлом | Логи доступа, изменения файлов (mtime), проверка на webshell, смена ВСЕХ паролей |
| Новый трек/песня | Файл на месте, проигрывается, обложка, метаданные, ссылка в портфолио |

## 🚨 Известные проблемы (уже найдено — в план включено)

1. **APP_ENV=development** — display_errors ВКЛЮЧЕН на проде (дыра + страшно клиентам) → переключить в production
2. **SMTP не настроен** — письма о заказах могут не доходить (mail() на хостинге ненадёжен) → настроить SMTP или Telegram
3. **admin123** — слабый пароль админки → сменить
4. **Мусор на сервере:** public/, public_html/, api.bak/, cleanup-*.php → разобрать/удалить
5. **Бэкапов нет** (не проверено) → настроить расписание
6. **Git рассинхронизирован** — сервер впереди GitHub → закоммитить
7. **.env root:root 600** — починили фолбэком, но чистое решение = chown tlax_ru_usr (нужен хостинг)

## 📌 Как это автоматизировать (план B)

- L0: cron-задача на Gateway (ежедневно утром) — скрипт `ops/check-tlax.sh` (curl по URL + размер лога + API get-tracks) → отчёт в чат
- L1: cron еженедельно (пн) + ручной e2e браузером
- L2: ручной аудит раз в месяц (напоминание cron)
- Алерт: если L0 нашёл проблему → сразу уведомление Boss
